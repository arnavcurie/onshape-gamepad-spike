Xbox Controller Driver — drive assembly mates in real time from a game controller, without leaving Onshape.


OVERVIEW

Opens as a right-side panel inside any assembly. Bind a mate to a controller input in a table, press Initialize, hold the deadman, and fly the mechanism.

Motion is written back as real mate values — the same numbers you would type into a mate's dialog — so limits and the solver behave exactly as for manual input. The panel adds no geometry and never edits a feature definition. Panel and viewport share one browser tab, so you watch the model move while you drive it.


REQUIREMENTS

  Browser      Chrome or Edge (Chromium).
  Controller   Any pad reporting the standard mapping with at least 4 axes:
               Xbox Wireless, Elite, Series X|S, most third-party XInput pads.
  Document     Must be open on a workspace; versions are read-only.
  Access       Write permission on the document; OAuth 2.

NO PLUGIN, DRIVER OR DOWNLOAD

The controller is read through the W3C Gamepad API, built into the browser. Nothing is installed and no extension is required. This is deliberate: an XInput or raw-HID integration would have been Windows-only. The Gamepad API is one interface with the same button and axis indices everywhere, so the panel behaves identically on Windows and macOS.

Windows — supported natively over USB, Bluetooth, or the Xbox Wireless Adapter. No setup beyond pairing.

macOS — macOS 11 Big Sur and later support Xbox controllers natively over Bluetooth. Pair from System Settings, Bluetooth, holding the pad's pair button. Only Bluetooth-capable models pair: Xbox One model 1708 and later, and all Series X|S. The 2013 model 1537 needs a cable.

On either platform, press a button on the pad after opening the panel: browsers do not enumerate a gamepad until it sends input.


SETTING UP A BINDING

Each row pairs one controller input with one mate.

  Input       Which control drives this row.
  Mate name   The mate to drive, typed exactly as in the feature list.
  Scale       Multiplier on the input. 1 normal, -1 reverses, 0.5 half speed.
  Home        Where the joint goes on a home command. Leave BLANK to return to
              the exact pose captured at Initialize.
  Range       Read-only. Declared limits, filled in by Initialize.
  Commanded,  Read-only. What the panel asks for, and what the assembly
  Actual      reports back.

Sub-assembly mates are addressed as instance name, slash, mate name, keeping the occurrence suffix — for example "Armatron_Grip <1>/Revolute_Grip". Top-level mates need no prefix, and two instances of one sub-assembly drive independently.

One input may drive several mates: add a second row on the same control, with +1 and -1 scales to open a pair of jaws symmetrically. Two rows on the same mate are rejected, since they would fight for the write each tick.


INITIALIZE (WHICH ALSO VERIFIES)

One button, because the two questions — does this binding resolve, and did the last session's writes actually land — are only worth asking together. It reads; it never writes. Initialize:

  • Resolves every mate name, including those reached through sub-assembly occurrences; a name missing its suffix is accepted only when unambiguous.
  • Reads each mate's limits from the feature definition of the element that owns it, filling the Range column. A mate with no limits reads "unlimited" and clamps at 180 degrees.
  • Seeds each joint's commanded value from its current position, so the first input moves the joint from where it actually is.
  • Captures the home pose: a snapshot of every value of every mate, not just the axis a row drives — which restores joints whose orientation no single number can describe.
  • Flags every row that will not work, with the reason on the row: "no such mate", "ambiguous", "duplicate", "not drivable", or "not moving" — the last meaning last session's writes were accepted and discarded.

Editing a mate name marks the table dirty and disables driving until you re-Initialize. Because the home pose is captured at Initialize, put the mechanism where you want "home" to be before pressing it.


CONTROLS

  LB (left bumper)   DEADMAN. Nothing moves unless it is held.
  LB + Back          Home all joints.
  LB + Start         Re-initialize.

The deadman is not optional and has no bypass: release it and every joint stops where it is. Homing sits behind it too, being the largest motion the mechanism makes.

Everything else is bindable — all four stick axes, both triggers, A, B, X, Y, RB, both stick clicks, all four D-pad directions. Guide is offered, though Windows usually claims it for the Game Bar.

Two per-row tools need no controller. Sweep runs one joint limit to limit and back at the same speed a fully deflected stick gives it, proving a binding moves the model and showing its travel. Home returns one joint, and Home All works from the panel too.


HOW INPUT BECOMES MOTION

Deadzone, per control: sticks 0.2, triggers 0.12, buttons none. Past the threshold the value is rescaled, not offset:

  output = (v - sign(v) * t) / (1 - t)

so motion ramps from zero at the deadzone edge instead of jumping to a deadzone's worth of speed.

Rate control, normalized to the joint's range. Sticks, buttons and the D-pad are rate controls: deflection is angular velocity, integrated over time, which is required for anything self-centering. The rate comes from the mate's own limits:

  degrees per second = |maxDeg - minDeg| / 3

Full deflection therefore crosses any joint's entire travel in about three seconds, whether it travels 20 degrees or 300, so a scale of 1 feels correct everywhere without tuning. A mate declaring no limits falls back to 60 degrees per second and clamps at 180.

Position control, with soft takeover. Triggers are position controls: the pull is the angle, mapped across the joint's full travel. Since a trigger cannot be moved to match the joint, its first sample would otherwise teleport the joint to wherever the trigger sits. Instead the binding stays inert until the trigger's implied angle passes within 2 degrees of the joint's current value. Until then the row reads "hold" and tells you which value to sweep through.


WRITE RATE

The panel samples at roughly 60 Hz but writes far less often. Three gates sit between input and the API:

  0.15 deg   Epsilon gate. A joint that moved less than this since its last
             write is not written; absorbs the noise a deadzone leaves.
  150 ms     Throttle. One write per interval at most, about 6 to 7 per
             second regardless of how fast input arrives.
  1 request  Batching. Every joint that moved goes in a single request. Six joints
             moving together cost one write.

Every write to an Onshape document creates a microversion, and the API is rate-limited per account. Writes are round-tripped, never synthesized: the panel reads the whole mate-value array, changes only the fields it drives, and posts it back.


LIMITATIONS

Every limitation below was measured. Most fail silently: the API returns success and the model does not move.

Closed kinematic loops cannot be driven. If a mate's value is determined by a closed loop — a four-bar linkage, cylindricals closing a chain, linkages tied by a gear relation — that value is a solver output, not an input. Onshape's UI can drag such a mechanism because dragging runs the solver; the API cannot set it. The write returns HTTP 200, no error, and nothing moves:

  loop closed  82.5775 deg -> commanded 79.5775 -> reads back 82.5775 IGNORED
  loop open    59.8643 deg -> commanded 56.8643 -> reads back 56.8643 DRIVABLE

Step size is not the issue: steps from 0.1 to 5 degrees all read back unchanged to four decimals. Three workarounds were tested and none works — flattening the sub-assembly, suppressing only the gear relation, and moving the instance by transform (HTTP 500 for a mated instance, against a clean 400 for a fixed one). The only fix is to open the loop.

Only the Default configuration can be driven. The mate-values endpoint does not honor a configuration parameter: it accepts one without complaint and operates on the Default variant regardless. There is no error to catch. A mate existing only in a non-default configuration cannot be driven — move the instance you intend to drive into the Default configuration. Limits are read correctly per configuration, so a row can show a correct range for a joint that will not move.

Ball mates. Onshape's documentation states that mate values may be set for all types except Ball, Fastened, Tangent and Width. A Ball exposes one drivable field over the API rather than three, and commanded and read-back values diverge away from zero because the orientation is path-dependent. Model a shoulder as stacked revolutes if it must be precise.

Other. Workspaces only. Mate names are case-sensitive and must match exactly. Not every device the browser calls a gamepad is one, so the panel requires 4 axes before accepting one.


DATA AND PRIVACY

The panel runs against a small backend that holds the OAuth client secret and proxies Onshape API calls.

Nothing about your model is stored. The backend holds the current assembly's mate values in memory for the duration of a session only, which is what lets the array be round-tripped. Bindings live in your browser's local storage, per element, and survive a reload. No geometry, document content or credentials are retained.
